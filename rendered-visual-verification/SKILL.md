# Rendered Visual Verification

## The rule

A report that the work is done is a claim to check, never the check
itself. Source files reading correctly does not mean the delivered
piece looks right. Verify the rendered version, or do not call it
delivered.

## Build the check list from the brief

- Before or during the build, extract the visible requirements:
  title or header, attribution or byline, colour and style
  requirements, layout, and every link or cross-reference the
  finished piece will claim to have.
- Always include the first view: a blank, black or placeholder
  opening is a failure even when the underlying file reads fine.
- For motion work, include a motion check: two frames inside one
  scene must visibly differ if the scene is meant to be animated.

## Inspect the rendered version

- Open the finished piece the way its audience will see it —
  rendered page, exported deck, playable file, final image — not
  only as source or code.
- Capture screenshots or extract frames and compare each check-list
  item against what is actually visible.
- Read the visible text in the render for the exact header,
  attribution and label wording the brief requires.
- Follow each claimed link in the rendered version and confirm it
  lands where the report says it lands.

## Fix and recheck before delivery

- Fix every mismatch found in the rendered version, then render and
  inspect again, so the corrected version is the one that was
  checked.
- Report a piece as delivered or live only after the recheck, and
  name what the render showed for the header, attribution, style
  and links.
- Name any item you could not inspect in rendered form as
  unverified in the delivery note rather than presenting the piece
  as fully checked.
- For expensive builds or publishes, show a still frame or
  screenshot for approval first, so a style miss costs one frame
  instead of a rebuild.
- Reuse the check list on the next version and add each new
  correction to it, so the same miss is not repeated across
  versions.
